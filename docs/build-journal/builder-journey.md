# Building a smarter TV picture frame

**Build journal · In progress · Last updated 29 October 2026**

This is a record of a real build, written for the Builders in Barcelona community. It follows the choices, experiments and corrections as we turn a Google TV dongle into a picture frame. It is not yet a finished installation guide. Steps marked **planned** still need to be tested.

## The idea

The starting point was a Samsung Frame TV connected to a Chromecast with Google TV 4K. Its built-in screensaver showed personal photos, but the compositions were not satisfying. A landscape image could fill the screen while cutting away the part that mattered.

The goal is a frame that chooses a useful focus, groups compatible portraits when a collage works better, and displays personal photos, art and moving pictures. It should show context such as the date, location, trip or artwork details briefly, then let the image speak for itself. A separate mode should display a hosted dashboard.

We are treating this as a personal project first. Other builders may choose different photo sources, storage, dashboards or hardware.

## 1. Define the experience before choosing the stack

We started with the outcome: a personal frame that is pleasant to look at and easy to update. We considered a custom app, but chose to investigate existing software first.

The intended first version now includes:

- **Photo selection:** select individual images and videos through Google Photos Picker. They stay in the frame rotation until removed.
- **Composition:** use subject-aware cropping, with a manual override. Automatically suggest collages when they improve the composition, while allowing manual grouping.
- **Context:** use available capture dates and GPS; suggest a trip match; identify art where a reliable match can be found. Allow corrections and omit uncertain details.
- **Modes:** Photos, Art, Mixed and Dashboard. Mixed mode has an adjustable balance. Dashboard mode displays a hosted page manually or on a schedule.
- **Video:** play muted by default, with an unmute control. Loop short videos until the slide interval ends; stop longer videos at that interval.
- **Control and resilience:** manage the frame from both a TV interface and a phone-friendly web app. Keep media locally available for offline playback.
- **Remote:** left and right change the current media; up and down change modes. A long centre-button press opens options for the current photo, including removing it from rotation.

These are product decisions, not features already built. See the [product plan](picture-frame-plan.md) for acceptance criteria and open questions.

## 2. Compare existing apps and sources

We looked at [PhotoWall](https://play.google.com/store/apps/details?id=net.nextlayertechnology.photowall) for visual inspiration. Its collage layouts were appealing, but its cropping did not consistently focus on the right part of the image for our use. It is closed source.

We selected Aerial Views as the **base to investigate**, not as proof that every desired feature already exists. It supports TV screensavers, network media, image and video playback, and metadata overlays. Its source also contains EXIF extraction code. We still need to test whether it can support our collage, dashboard, offline and management requirements without extensive changes.

[Immich Android TV](https://github.com/giejay/Immich-Android-TV) is another open-source option if Immich becomes the library. We also found [Digital Photo Frame](https://github.com/rwkaspar/digital_photo_frame), a Raspberry Pi project that claims support for Google Photos shared album links. Its connector is unverified for this project.

## 3. Decide how photos enter the frame

We explored a shared Google Photos album, scheduled Google Takeout exports and a personal instance of Krill, an existing photo-library project. The planned selection flow uses **Google Photos Picker** to copy selected media into a frame library. For the first implementation, we chose the existing Krill library; a personal instance and Picker import remain planned.

Google changed its Photos APIs in 2025. The Library API cannot generally list existing albums that another app did not create. Picker lets a person select specific media, but it is not automatic album synchronization. [Google's API changes](https://developers.google.com/photos/support/updates)

The Picker's documented metadata includes creation time and dimensions, but does not list GPS. We need to inspect actual downloaded photos and confirm what metadata survives. We also need to review Google's current policy for long-lived storage in this specific use. [Picker media reference](https://developers.google.com/photos/picker/reference/rest/v1/mediaItems) · [Photos API policy](https://developers.google.com/photos/support/api-policy)

If a photo is deleted in the frame, the plan is to remove its stored Cloudflare copy and device cache as well. The Picker does not establish a way to monitor deletion from Google Photos itself. If that cannot be detected, the frame will provide manual removal.

## 4. Choose an initial crop strategy

We considered [smartcrop.js](https://github.com/jwagner/smartcrop.js), which scores candidate crops and can accept externally detected face regions. We chose to test **Cloudflare Images** first because Krill already uses Cloudflare and its image transformations can both resize images and select a focal area. Cloudflare documents automatic saliency and face-based gravity, plus explicit focal coordinates. [Cloudflare Images options](https://developers.cloudflare.com/images/optimization/features/)

This is a hypothesis, not a verified quality claim. The experiment must compare automatic and face-aware crops against Al's own landscapes, portraits, groups and artwork. A manual correction remains necessary. Collage selection is a separate problem from cropping.

## 7. Connect the TV over Wi-Fi

**In progress.** The plan is to install Tailscale on the Google TV and connect it to the same tailnet as the VPS. Then enable developer options and wireless debugging, pair ADB, and install the baseline APK. We will document the actual steps and device-specific results after testing them.

**Observed:** Tailscale reached the TV through a relay. Wireless ADB pairing succeeded using the temporary pairing port and code shown on the TV. Pairing is separate from connecting: the wireless debugging screen also shows a connection port.

To reproduce the connection on a compatible device:

1. Install Android SDK Platform Tools on the computer. Enable developer options and wireless debugging on the TV. Make sure the computer can reach the TV; in our setup both devices were on the same Tailscale network.
2. On the TV, open the pairing-code screen. Use the TV's reachable address and the **pairing port** shown there. Set `TV_IP` and `PAIR_PORT` in the shell, then run `adb pair "$TV_IP:$PAIR_PORT"`. Enter the displayed code at the prompt.
3. Return to the main Wireless debugging screen. Set `CONNECT_PORT` to its separate connection port, then run `adb connect "$TV_IP:$CONNECT_PORT"` and `adb devices`. The TV should appear with status `device`.
4. If the TV restarts or the debugging port changes, read the current connection port and run `adb connect` again. Re-pair only if the existing pairing was removed. Turn off wireless debugging or revoke the pairing when it is no longer needed.

Do not share the pairing code, device address or connection port in a public guide. Android's [ADB documentation](https://developer.android.com/tools/adb) describes pairing and troubleshooting; menu labels and network behavior can vary by device.

After building the beta debug APK and connecting the TV, install that build from the repository root:

```sh
adb -s "$TV_IP:$CONNECT_PORT" install -r app/build/outputs/apk/beta/debug/app-beta-debug.apk
```

The `-s` option selects the intended device if ADB sees more than one. The `-r` option updates a compatible existing installation while retaining its data; Android rejects an update signed with a different key. This command installs a debug build, not a signed release. Our frame changes are still local, so cloning the public fork today does not reproduce the modified app.

### Frame schedule and art cadence (UNS-1752, 5 November)

The single dashboard window became a Schedule section in the TV settings. One rule sets the days, the start and end times, how often the dashboard appears and how long it stays. The default is the owner's target: weekdays from 07:00 until 18:00, the dashboard for one minute every five minutes, with photos and videos in between. After 18:00 and at weekends only pictures play. A window that crosses midnight belongs to the day it starts on; equal times mean the whole day; clearing every day turns the schedule off. An existing window carries over as every day with the dashboard on throughout, which was the old behaviour. The old disabled default takes the new weekday default.

A manual change with up or down, or Back on the dashboard, holds until the schedule's next change, which is the next dashboard start or end. The schedule then resumes. The check runs every five seconds instead of fifteen so a one-minute slot stays accurate.

Mixed mode can now space art as X percent of slides, one in every X slides, or every X minutes. The default is 30 percent, matching the plan's 70/30 balance; only an explicitly changed old percentage is kept.

Twelve focused unit tests passed, covering the weekday and weekend boundaries, the 18:00 cutover, overnight windows, settings parsing and the cadence math. The beta debug APK built and the formatting check passed. Behaviour on the TV is not yet verified.

### Server-side portrait pairs (UNS-1754, 5 November)

On 5 November (UNS-1754), we moved portrait pairing from the TV to Krill. On the TV, two portraits taken on the same day at the same place were shown singly with blurred sides. The frame's local planner paired only photos with shared tags, and it had no access to capture time or place. Planning also took about 13 seconds at startup. In the new design, Krill reads capture time and GPS from each portrait's EXIF and computes an average colour with a 1 × 1 Cloudflare Images transform. Picker imports fall back to their stored capture time. Krill pairs two portraits only on reliable evidence: photos taken within 3 hours (same occasion), or within 36 hours with GPS fixes no more than 25 km apart (same trip). Place must not contradict the time evidence. Colour and tags only rank eligible candidates. Krill stores the partner, score and reason in additive migration 051 and adds an optional `pair` object to the frame feed. Pairing runs on upload and in a resumable backfill that reads 40 portraits every 5 minutes. A flag gates the feature. The frame now forms a collage only when both photos name each other and each can fill half the screen without enlargement. Otherwise it keeps the existing single-photo layout: a focal crop for landscapes, and fit plus blur for portraits. The rotation planner now looks up partner IDs instead of scoring candidates. "Show these photos separately" and "Reset collage choices" are unchanged. The playlist cache moves to schema version 6. The upgrade rebuilds the cache once from Krill, so cached photos carry their partners. Focused unit tests and `assembleBetaDebug` pass. Deployment, the backfill and testing on the TV still need Al's approval and have not been done. Install the APK after the backfill has covered the library.

### Verified captions (UNS-1753, 5 November)

On 5 November, we addressed a caption bug: photos imported through Google Photos showed their upload file name and a raw UTC timestamp. The cause was in Krill. Picker imports store the file name as the title and Google's UTC capture time as the description, and the frame joined the two. Before changing the design, we checked all 11 imported originals, recording only whether each field was present. Every one had EXIF with the camera's local capture time and timezone offset. None had GPS coordinates, because Google strips location from Picker downloads. A place therefore cannot come from Google Photos imports. Al decided that these imports show only the capture time, and that place comes from GPS on direct uploads, including the planned iPhone share-sheet upload (UNS-1755).

Krill now has optional caption fields: place (attraction, neighbourhood, city and country), camera local time and its offset, and artwork title and artist, with confidence and source. These are added by migration 052. A scheduled enrichment step reads EXIF from the stored original and reverse-geocodes GPS through OpenStreetMap Nominatim, at no more than one request per second. Museum imports take title and artist from their catalogue record. Personal art tagged `art` can be identified by a vision model through the existing AI controls, which is off by default, and the result is stored only at confidence 0.85 or above. Enrichment processes the newest uploads first, ten per five-minute tick, with three attempts per item. Any upload path is covered, whether or not it has GPS. The frame shows the artwork title and artist, or otherwise the most specific known place and a time such as "Thu 22 Oct 2026, 4:07 pm". It leaves out unknown fields. Older captions without these fields have file names and raw timestamps removed. By default, the caption corner fades after eight seconds and the clock remains. Unit tests and the debug build passed.

With Al's approval, we deployed this to Footage Rodeo on 5 November. We took a D1 Time Travel bookmark, applied only migration 052 as a single file, deployed from `uns-1745-frame-current`, and enabled enrichment with the art vision model left off. The first batches claimed photos but enriched none. In production, D1's change count also includes the search-index trigger on `media`, so a successful claim reported four changes, and the code skipped every claimed photo without recording a failure. The local SQLite tests count only direct row changes, so they missed it. Krill now confirms each claim from the row it returns ([Krill PR #59](https://github.com/al-unsoldgroup/krill-photo-library/pull/59)). The next batch enriched 10 photos with no failures. All 10 have local time and offset. None has a place, as expected for Google Photos imports, and none has artwork. Displaying the captions on the TV remains to be verified. A first TV check showed no file names or timestamps, and the caption corner faded. However, the upgraded app kept showing a compact date. It had restored its cached playlist, and its record of a recent caption refresh still matched, so it never fetched the new fields. The refresh key now includes a caption format version, so the first screen after an upgrade fetches captions immediately; the existing cancellation fence is unchanged. A one-time settings migration also puts the Krill caption first in every saved photo caption list, so Krill photos show their caption instead of a bare compact date. The clock is unchanged. Unit tests cover both. A second TV check has not been done.

For the direct path, an iOS Shortcut in the Photos share sheet posts each original file to a new Krill endpoint, authenticated by a revocable per-device token. No native app or Mac build is required. iOS removes GPS before sharing unless the share sheet's Options → Location setting is on. The endpoint stores the original bytes unchanged, so a shared photo enters the same caption-enrichment queue, and the next cron adds its place and capture time. A test with a synthetic GPS-tagged JPEG confirms both steps. The work is in [Krill PR #57](https://github.com/al-unsoldgroup/krill-photo-library/pull/57). A real iPhone share is still untested.

### Personal art in Art and Mixed modes (UNS-1750, 10 November)

Personal art is a photo Al marks as art in Krill, on one item or on a multi-select. The mark is the existing `art` tag. A title and artist typed by hand are stored in the caption fields from migration 052 as verified, with source `manual`, and caption enrichment no longer overwrites them. The frame feed now also sends `category: "art"`. New Krill migration 058 bumps the library revision when the art tag or the artwork caption changes, so the TV picks up the change instead of waiting up to a day.

On the frame, an item tagged or categorised as art populates the ART category, so Art mode joins the mode cycle and Mixed mode uses it at the existing 30 percent default. Art without a manual crop point is shown whole: fit to the screen on a dark neutral matte, with no server crop, no focal crop and no blurred backdrop. When Al sets a crop point with the existing focus editor, art is cropped around it like a photo. Art is never placed in a collage. The caption shows title and artist, or the artist alone.

This follows the task decision for this milestone (uncropped by default) rather than the plan's earlier "art fills the screen by default" line. The full unit suite, the formatting check and `assembleBetaDebug` passed. Nothing was installed on the TV in this step.

Review fix, 10 November: marking or unmarking art after an item was already cached did not reach the frame. The full refresh wrote captions and pairing but never rewrote tags on existing cached rows, so the item stayed a photo until the cache was rebuilt. The pairing refresh now carries the feed tags into the cached row and the in-memory item, and rebuilds the mode index when they change. New tests add and remove the art tag on a cached row and on a window item. Full unit suite: 698 tests, 0 failures; formatting check and `assembleBetaDebug` passed.
